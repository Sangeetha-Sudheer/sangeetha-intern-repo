# Help Strategy Reflection

## When do I prefer using AI vs. searching Google?

I prefer using AI when I need help understanding a concept, breaking down an error, comparing possible solutions, or getting step-by-step guidance.

AI is useful when I can provide context such as error messages, code snippets, and what I have already tried. It can help explain the problem in simpler terms and suggest possible next steps.

I prefer using Google when I need:

- official documentation;
- exact library or framework behaviour;
- recent version-specific information;
- known GitHub issues;
- Stack Overflow discussions;
- release notes or changelogs.

For technical decisions, I should verify important AI-generated suggestions using official documentation or reliable sources.

## How do I decide when to ask a colleague instead?

I would ask a colleague when:

- I have already tried reasonable troubleshooting steps without success;
- the issue is specific to Focus Bear's codebase or architecture;
- I need business or product context that is not available publicly;
- the problem could affect production or user data;
- there is a security or privacy concern;
- the task is urgent and spending more time troubleshooting alone would delay the team;
- I need confirmation before making a significant architectural change.

When asking for help, I should explain:

- what I am trying to do;
- what I expected to happen;
- what actually happened;
- the error message;
- what I have already tried.

This makes it easier for another developer to help efficiently.

## What challenges do developers face when troubleshooting alone?

Troubleshooting alone can be difficult because developers may:

- spend too long focusing on the wrong cause;
- miss obvious mistakes because they have looked at the same code for too long;
- misunderstand an error message;
- lack context about a specific codebase;
- use outdated documentation;
- become frustrated and make unnecessary changes;
- introduce new bugs while trying multiple fixes;
- waste time solving a problem another team member already understands.

A structured troubleshooting process helps reduce these problems.

## My Troubleshooting Strategy

When I encounter a coding problem, I will follow this approach:

1. Read the error message carefully.
2. Reproduce the problem consistently.
3. Check recent code changes.
4. Inspect logs and relevant files.
5. Try a small and safe fix.
6. Search official documentation or Google for the exact error.
7. Use AI to explain the problem, compare solutions, or help interpret the error.
8. Verify AI suggestions before applying them.
9. If I am still blocked, ask a colleague and provide clear context about what I have already tried.

## Factors I consider

### Complexity

For simple syntax errors or common framework errors, I can usually troubleshoot independently using documentation, Google, or AI.

For complex architectural or project-specific problems, asking a colleague earlier may save time.

### Sensitivity of information

I should never paste passwords, API keys, authentication tokens, private user data, confidential company information, or sensitive source code into public tools or services unless they are specifically approved for that information.

Sensitive issues should be handled using approved internal tools and discussed with the appropriate team member.

### Urgency

If a problem is low priority, I can spend more time researching and learning independently.

If the issue is blocking important work or affecting users, I should escalate sooner rather than spending too long troubleshooting alone.

## Key Learning

The main lesson is that Google, AI tools, and colleagues each serve different purposes.

AI can help explain and explore solutions, Google and official documentation help verify technical information, and colleagues provide project-specific knowledge and human judgement.

The best approach is not to rely on only one resource, but to choose the appropriate tool based on complexity, sensitivity, urgency, and the type of information required.
